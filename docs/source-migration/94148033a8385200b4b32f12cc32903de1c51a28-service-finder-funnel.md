# Service finder measurement contract

## Decision and boundary

Measure whether the public service finder helps a visitor identify a suitable MALIEV process and continue toward the existing quotation journey. Finder events are diagnostic GA4 events only. They must not be GA4 key events, Google Ads conversions, primary actions, or bidding goals. The existing post-persistence `maliev_lead_submitted` / `generate_lead` boundary remains the sole lead outcome.

The finder emits only stable answer IDs, service IDs, path IDs, numeric step numbers, and an optional anonymous page-visit correlation value. It must never send rendered answer labels, customer text, contact data, files, query parameters, `journey_id`, or `transaction_id`.

## Event dictionary

| Event | Fires | Additional fields | Deduplication |
|---|---|---|---|
| `service_finder_started` | First answer, optional-step skip, or skip-to-results action | none | Once per finder reset cycle |
| `service_finder_step_completed` | A selected active step advances | `step_key`, `answer_id`, `step_number` | Once per advance action |
| `service_finder_step_skipped` | An optional active step is skipped | `step_key`, `step_number` | Once per skip action |
| `service_finder_completed` | Results are shown with all five required answers | `recommended_service_ids`, `finder_path`, `partial=false` | Each results render after a changed path |
| `service_finder_results_viewed` | Results are shown without all required answers | `recommended_service_ids`, `finder_path`, `partial=true` | Each partial-results render after a changed path |
| `service_finder_recommendation_clicked` | A recommended service link is activated from complete results | `service_id`, `finder_path` | Each qualifying click |

All finder events may include `finder_session_id`: a UUID v4 created with `crypto.randomUUID()` once when the finder initializes. It is held only in memory for that page visit, so navigation or reload generates a new value. If secure randomness is unavailable, the field is omitted. The value is not handed off to quotation URLs and is not a substitute for the persisted-quotation `journey_id` or `transaction_id` boundaries.

## GTM and GA4 configuration

- Container: `GTM-KHDDLVRR`; current live version observed: 11.
- Add a data-layer variable `DLV - finder_session_id` and map it to an event parameter named `finder_session_id` on the finder diagnostic tags: `GA4 - service finder started`, `GA4 - service finder step completed`, `GA4 - service finder completed`, and `GA4 - service finder recommendation clicked`.
- Add equivalent custom-event tags/triggers for `service_finder_step_skipped` and `service_finder_results_viewed` only if those diagnostic events are needed in GA4 reporting; do not route either event to Ads.
- Register `finder_session_id` only as an event-scoped diagnostic parameter if GA4 reporting needs it. Do not use it as a user property, audience input, key event, conversion, or bidding signal.
- Existing live mappings remain: completed maps `recommended_service_ids` and `finder_path`; recommendation click maps `service_id` and `finder_path`; step completed maps `step_key`, `answer_id`, and `step_number`.

## Validation gate

Before treating the contract as live:

1. Inspect the local `dataLayer` across start, step completion, results, and recommendation-click actions; verify one UUID-shaped `finder_session_id` is reused only for that page visit, a reload generates a new value, and unavailable secure randomness omits it.
2. Validate granted and denied consent states in GTM Preview/Tag Assistant.
3. Confirm every mapped finder event fires its intended GA4 diagnostic tag, and no finder trigger fires a Google Ads conversion tag.
4. Confirm `finder_session_id` and existing fields in GA4 DebugView without `journey_id`, `transaction_id`, PII, or query-string values.
5. After deployment and natural traffic, read back the event counts and parameter availability. Keep `generate_lead` as the sole finder-adjacent conversion/key event.
